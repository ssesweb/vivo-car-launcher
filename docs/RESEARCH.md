# 研究记录

本文件整理自现有代码与现场验证。厂商私有实现的名称用于定位研究线索，不附带厂商反编译源码。

## 底部安全区与全屏是两个验收项

测试屏幕为 3283 x 1746，dock 上沿约为 y=1536。在部分状态中，窗口 frame 覆盖全屏，但应用内容边界为 3283 x 1536。只有画面底部控件正确显示、能够操作，才说明安全区行为满足需求。

早期把问题理解为隐藏 dock，后续用户明确要求应用底部合理显示。因此不再把 dock 消失本身作为成功标准。

## 原生启动与直接启动

通过原生桌面点击应用，系统可能携带或触发额外的投屏与窗口适配行为。直接执行 am start 可能绕过相关路径。不能仅根据两次启动的 displayId、窗口 frame 或 inset 字段相同，就认定实际内容布局相同。

曾尝试模拟原生图标点击。透明留白使车启发出的模板与车机图标比例不一致，裁去留白后番茄匹配成功。该方案需要左右翻页寻找图标，用户不需要此行为，因此已经从应用启动流程停用。

## vivo 运行时多窗口接口

现有 CarSessionBridge 使用反射访问 ActivityManager 服务的 `getMultiLandsAppsForVirtual` 和 `changeMLAppEnableWithBundleForVirtual`。

实验使用 displayId、packageName、enable、isKillProcess=false 等参数，针对运行时 map 中已存在的应用处理多窗口状态。将 enable=false 称为进入全屏方向，仅表示原生设置路径的一部分，不表示真实画面全屏已经验收。

接口调用成功、状态读回一致、应用可见、画面正确及重连后保留是不同层次，需分别验证。

## 应用名单

手机可启动应用枚举，与厂商允许投屏、推荐目录和桌面显示的名单不是同一件事。车启的 QUERY_ALL_PACKAGES 修复的是手机端列表可见性，不代表开放全部投屏能力。

历史研究显示推荐目录可能由本地初始化与异步服务端数据共同形成。修改一次运行时状态，不能证明网络刷新或重新连接后会保留。当前仓库不声称已完成名单开放。

## 已尝试的其他路径

- AppFullScreenEv 属于 networking 内部事件，观察到的多个发布点与地图处理有关，尚未建立通用外部调用入口。
- appFullScreen 持久字段与运行时多窗口状态有联系，但单独修改其中之一不代表完整复现原生行为。
- 试过的 am task resize 调用没有改变目标窗口 frame；命令返回成功不能作为布局成功证据。

下一步以直接启动、安全区、按需全屏为主线，避免重新引入自动翻页找图标。
